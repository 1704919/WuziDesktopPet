## 4. main.gd 健康情况

`main.gd` 当前约可分成：

```text
初始化、配置、窗口
↓
右键菜单、动作点播
↓
对话、昵称
↓
天气、提醒
↓
文件拖入
↓
动态命中、鼠标穿透
↓
动画加载与播放
↓
输入、拖拽、抛掷、Q 弹
↓
点击反应、动作协调
↓
睡眠、惊醒、用户活动
```

当前问题不是“函数写得差”，而是**一个文件掌握太多不同领域的状态和行为**。

后续新增任何以下能力都容易再次进入 Main：

- 新动作状态；
- 换装；
- 新右键菜单；
- 更多睡眠逻辑；
- 新交互；
- 更多输入行为。

因此推荐对 Main 做渐进式拆分。

### 推荐原则

**只搬家，不改行为。**

每次只抽出一个完整职责块，保持原参数、原返回值、原时序、原信号、原状态判断不变。

优先候选顺序：

1. 动画播放 / clip runtime；
2. 拖拽 + 抛掷；
3. 睡眠状态；
4. 右键动作菜单。

不建议一次性重写 Main。

## 6. 文件处理安全性

当前文件处理属于项目中设计最成熟的部分之一。

已有：

- 预览后再执行；
- frozen plan；
- SHA-256 计划版本；
- 参数变化会使旧确认失效；
- 执行前重新检查源文件；
- 不覆盖现有目标；
- Windows native move/copy 本身也禁止覆盖；
- A↔B 和多文件循环使用两阶段重命名；
- 改名失败尝试恢复；
- 无法恢复时保留 recovery_path；
- 图片转换写到独占临时目录后再提交；
- 部分失败不删除失败项；
- 取消只停止未开始项目；
- WorkerThreadPool 不直接操作 UI Node。

结论：

**不要为了“轻量化”削减这部分安全保护。**

这里的复杂度是必要复杂度。

## 7. 其他工程问题

### 7.1 当前不是 Git 仓库

检查结果：

```text
fatal: not a git repository
```

这是当前最值得优先补的工程基础。

建议在任何结构瘦身前：

1. 初始化 Git；
2. 建立合适的 `.gitignore`；
3. 提交当前稳定基线；
4. 之后每拆完一块并通过测试，单独提交一次。

### 7.2 历史日志较多

`docs/` 当前扫描到约：

- 2599 个文件；
- 约 57.8 MB。

其中绝大部分是 baseline 日志和 JSON。

短期无害，但长期会降低交接效率。

### 7.3 backups 较多

`backups/` 已经存在多个阶段和专项快照。

在 Git 建立以后，普通源码修改不再需要继续制造同等密度的手工源码备份。

大型二进制素材仍可继续采用独立备份策略。

### 7.4 Python 依赖没有统一声明

素材工具实际依赖：

- NumPy
- Pillow
- imageio-ffmpeg

建议以后补最小依赖清单。

### 7.5 本机路径硬编码

多个工具默认：

```text
D:\Godot\Godot_v4.7-stable_win64.exe
```

以后换机或发布时再处理即可，不是当前阻塞项。

### 7.6 潜在遗留文件

`popup_card_window.gd` 当前搜索不到正式引用。

在没有再次确认前，不建议仅为了清理直接删除。

### 7.7 movement_catalog.json

`main.gd` 存在默认路径：

```text
res://config/movement_catalog.json
```

当前文件不存在。

但 `pet_behavior.json` 中：

```json
"roaming": {
  "enabled": false
}
```

所以现在不是实际故障。

等未来启用 roaming 时再处理。

## 8. 推荐处理顺序

### P1：先建立 Git 基线

不要先拆代码。

### P1：渐进拆 main.gd

每次只拆一个职责块。

### P2：渐进拆 batch_file_window.gd

优先拆 UI / 样式 / 文件选择，不动 Planner / Executor 语义。

### P2：保持每步测试

每个拆分步骤完成后至少：

```powershell
py -3 tools/run_baseline_tests.py
```

如只涉及文件工作台，可先运行专项：

```powershell
py -3 tools/run_baseline_tests.py --only stage5_file_planner_smoke stage5_file_executor_smoke
```

专项通过后，最终仍应再跑完整离线基线。

### P3：以后处理依赖、日志和路径

这些属于工程卫生，不应和核心逻辑瘦身混在同一个提交中。

---

## 9. 本轮建议的瘦身总原则

1. **只搬家，不改行为。**
2. **一次只拆一块。**
3. **拆完立即测试。**
4. **测试不通过立即停止，不继续下一块。**
5. **先 Git 基线，再修改源码。**
6. **每一块独立提交。**
7. **不要顺手修 Bug、改 UI、改参数、改命名或优化算法。**
8. **Planner / Executor / native bridge 暂时视为稳定边界。**
9. **以现有 smoke test 和阶段五基线作为行为基准。**
10. **发现原有问题时先记录，不夹带到“纯搬家”提交里修。**

## 10. 最终判断

**推荐继续在当前工程上渐进式维护。**

不需要重写。

当前正确路线是：

```text
初始化 Git
↓
提交稳定基线
↓
选一个职责块
↓
只搬家
↓
专项测试
↓
完整回归
↓
提交
↓
再拆下一块
```

如果坚持这一原则，`main.gd` 和 `batch_file_window.gd` 可以在不改变现有行为的前提下逐步瘦身，并显著降低后续阶段继续开发的维护成本。
